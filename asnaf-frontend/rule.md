# سند جامع قوانین معماری، مهندسی و توسعه فرانت‌اند (rule.md)

این سند مرجع رسمی، الزام‌آور و حاکم بر تمام فرآیندهای توسعه در مخزن فرانت‌اند (`asnaf-frontend`) است. در این مخزن **فقط و فقط کدهای فرانت‌اند** پروژه قرار می‌گیرد. تمامی توسعه‌دهندگان و ماژول‌ها ملزم به رعایت ۱۰۰٪ این قوانین مهندسی می‌باشند.

---

## ۱. اصول بنیادین معماری فرانت‌اند (Core Architecture)

### ۱.۱. معماری ماژولار و مبتنی بر دامنه (Feature-Driven / Modular Domain)
* ساختار سورس‌کد باید بر اساس تفکیک دامنه‌های کسب‌وکار (مانند اصناف، پرونده‌ها، کاربران، احراز هویت، گزارش‌ها و ...) سازمان‌دهی شود.
* هر دامنه باید اجزای اختصاصی خود (کامپوننت‌ها، استورها، سرویس‌های API، تایپ‌ها و کامپوزیبل‌ها) را به صورت خودکفا نگهداری کند تا مقیاس‌پذیری و نگهداری‌پذیری کدها به حداکثر برسد.

### ۱.۲. اصل تک‌مسئولیتی و تفکیک کامپوننت‌ها (SRP & Component Separation)
* **صفحات سبک (Lean Pages):** هیچ فایلی در دایرکتوری `src/pages/` نباید حاوی منطق‌های محاسباتی سنگین، کدهای پیچیده دستکاری استیت یا قالب‌های بزرگ باشد. صفحات صرفاً نقش هماهنگ‌کننده (Orchestrator) کامپوننت‌های فرعی و تزریق‌کننده Layout را دارند.
* **تفکیک قطعی Smart و Dumb Components:**
  * **Presentational (Dumb) Components:** صرفاً ورودی‌ها را از طریق `props` دریافت کرده و رویدادها را از طریق `emits` ارسال می‌کنند؛ این کامپوننت‌ها فاقد دسترسی مستقیم به Store یا API هستند.
  * **Container (Smart) Components:** وظیفه اتصال به Storeها، فراخوانی اکشن‌ها و هدایت داده‌ها به سمت کامپوننت‌های ارائه‌دهنده را بر عهده دارند.
* **تفکیک دیالوگ‌ها و ابزارها:** کلیه مودال‌ها، دیالوگ‌ها و فرم‌های فرعی باید به صورت فایل کامپوننت مستقل پیاده‌سازی شوند و نباید به صورت کدهای طولانی در بدنه صفحه اصلی قرار گیرند.
* **رعایت اصل DRY:** کامپوننت‌ها و الگوهای تکرارشونده باید در `src/components/common/` انتزاع و مستقر شوند.

### ۱.۳. لایه‌بندی شفاف لایه‌های برنامه (Separation of Concerns)
معماری فرانت‌اند موظف به رعایت ۴ لایه مستقل زیر است:
۱. **لایه ارائه (UI Layer):** فایل‌های کامپوننت Vue، Layoutها و قالب‌ها.
۲. **لایه وضعیت (State Layer):** استورهای متمرکز Pinia برای حفظ و انتشار دیتای سراسری.
۳. **لایه منطق کسب‌وکار (Logic Layer):** کامپوزیبل‌ها (`composables`) جهت کپسوله‌سازی منطق‌های قابل استفاده مجدد.
۴. **لایه دسترسی به داده (Data Access / API Layer):** کلاینت Axios، ریپازیتوری‌های API و مدل‌های DTO.

### ۱.۴. پیشگیری از نشت حافظه (Memory Leak Prevention)
* لغو لیسنرهای سراسری (مانند `window.addEventListener`، `ResizeObserver`، تایمرها و `setInterval`) در هوک چرخه حیات `onBeforeUnmount` الزامی است.
* درخواست‌های شبکه در حال انتظار هنگام تعویض صفحه یا از بین رفتن کامپوننت باید به کمک `AbortController` متوقف شوند.

## ۲. الزام مطلق استفاده از Quasar CLI و استانداردهای کوازار

### ۲.۱. محوریت کامل Quasar CLI (`@quasar/cli`)
* **کلیه دستورات بیلد، توسعه، اجرا و بازرسی پروژه باید منحصراً از طریق Quasar CLI صورت پذیرد:**
  * اجرای سرور توسعه: `quasar dev`
  * بیلد خروجی پروداکشن: `quasar build`
  * پاک‌سازی کش و بیلد: `quasar clean`
  * بازرسی پیکربندی بیلد: `quasar inspect`
* **ممنوعیت اجرای مستقیم ابزارهای زیربنایی:** از فراخوانی مستقیم دستورات `vite` بدون کوازار یا اضافه کردن اسکریپت‌های ناهماهنگ با Quasar CLI اکیداً خودداری شود.
* استفاده از Quasar CLI Generatorها برای ایجاد استاندارد ساختارها توصیه می‌شود (`quasar new component <name>`, `quasar new store <name>`, `quasar new page <name>`).

### ۲.۲. پیکربندی رسمی در `quasar.config.ts`
* فایل کانفیگ اصلی پروژه منحصراً `quasar.config.ts` است.
* **تنظیمات روتر:** فعال‌سازی اجباری حالت `createWebHistory` بدون کاراکتر هش (`vueRouterMode: 'history'`).
* **درخت‌تکانی کامپوننت‌ها (Tree Shaking):** پلاگین‌ها و کامپوننت‌های کوازار باید به صورت هدفمند و بهینه در فایل کانفیگ تعریف شوند تا حجم نهایی باندل به حداقل ممکن برسد.
* **پلاگین‌های استاندارد کوازار:** پلاگین‌های رسمی مانند `Notify`، `Dialog`، `LoadingBar`، `Meta` و `LocalStorage` در بخش `framework.plugins` ثبت و پیکربندی شوند.

## ۳. استانداردهای زبان Vue 3 و استایل اسکریپت

### ۳.۱. استفاده انحصاری از `<script setup lang="ts">`
* کلیه کامپوننت‌ها، صفحات و لایوت‌ها باید منحصراً با ساختار **Vue 3 Composition API** و سینتکس `<script setup lang="ts">` نوشته شوند.
* استفاده از Options API یا دستور سنتی `export default defineComponent({ ... })` در سراسر پروژه اکیداً ممنوع است.

### ۳.۲. تعریف دقیق و تایپ‌شده ورودی‌ها و خروجی‌ها
* **تعریف Props:** صرفاً با ماکروی نوع‌محور `defineProps<{ ... }>()` به همراه `withDefaults` برای مقادیر پیش‌فرض:
  ```typescript
  interface ComponentProps {
    readonly id: number;
    readonly title: string;
    readonly isActive?: boolean;
  }

  const props = withDefaults(defineProps<ComponentProps>(), {
    isActive: false,
  });
  ```
* **تعریف Emits:** تعریف دقیق نوع و آرگومان‌های رویدادها با `defineEmits<{ ... }>()`:
  ```typescript
  const emit = defineEmits<{
    (e: 'update:modelValue', value: string): void;
    (e: 'submit', payload: SubmitPayload): void;
  }>();
  ```
* **پرهیز از جهش دوطرفه کنترل‌نشده:** از جهش مستقیم پراپ‌ها خودداری شود. تغییرات وضعیت باید همواره از طریق رویداد یا مدل دوطرفه استاندارد (`v-model`) به والد گزارش شود.

## ۴. قوانین سخت‌گیرانه تایپ‌اسکریپت و اعتبارسنجی کد (Strict TypeScript)

### ۴.۱. سیاست عدم تحمل `any` (Zero-any Policy)
* استفاده از تایپ `any` تحت هر شرایطی ممنوع است و تخلف مهندسی محسوب می‌شود.
* در سناریوهای داده‌های ناشناخته یا پاسخ‌های اولیه شبکه، از `unknown` به همراه Type Guard، فیلترهای اعتبارسنجی (مانند Zod) یا Generics استفاده شود.

### ۴.۲. تنظیمات سخت‌گیرانه کامپایلر (`tsconfig.json`)
* فعال‌سازی دائم شاخص‌های:
  * `"strict": true`
  * `"noImplicitAny": true`
  * `"strictNullChecks": true`
  * `"noUnusedLocals": true`
  * `"noUnusedParameters": true`
  * `"exactOptionalPropertyTypes": true`
* **وارد کردن مجزای تایپ‌ها:** کلیه تایپ‌ها و اینترفیس‌ها باید صراحتاً با پیشوند `import type` وارد شوند (`consistent-type-imports`):
  ```typescript
  import type { UserProfile, UserRole } from 'src/types/user';
  ```
* **متغیرهای بدون استفاده:** در صورت نیاز به تعریف آرگومان یا متغیر برای رعایت ساختار اینترفیس که بلافاصله استفاده نمی‌شود، نام آن باید با کاراکتر زیرخط (`_`) آغاز شود (مانند `_event`, `_index`).

### ۴.۳. قوانین لینتر و فرمت‌بندی (ESLint 9 & Prettier)
* استفاده از معماری جدید **Flat Config** کوازار و ESLint در فایل `eslint.config.js`.
* **ممنوعیت مطلق ابزارهای دیباگ در کد پروداکشن:** استفاده از `debugger` و `console.log` در سورس‌کد ممنوع است و باید در بیلد نهایی توسط پلاگین حذف شوند (`drop_debugger`, `drop_console`).
* **استانداردهای ادیتور و فرمت‌کننده:**
  * انکودینگ: `UTF-8`
  * نوع انتهای خطوط: `LF` (لینوکسی/یونیکس)
  * تورفتگی (Indentation): منحصراً ۲ فاصله (Space)
  * طول مجاز سطرها: حداکثر ۱۰۰ کاراکتر
  * گیومه منفرد (`'`) برای رشته‌ها به جای گیومه جفت (`"`)
  * حضور خط خالی در پایان تمام فایل‌ها (`insert_final_newline = true`).

## ۶. معماری لایه شبکه، سرویس‌های API و مدیریت خطا

### ۶.۱. ممنوعیت فراخوانی مستقیم در صفحات و کامپوننت‌ها
* هیچ صفحه یا کامپوننتی حق ندارد به صورت مستقیم متدهای `axios.get`، `axios.post` یا `fetch` را صدا بزند.
* تمامی تعاملات خارجی با سرور باید از طریق **سرویس‌های اختصاصی در `src/api/` یا `src/services/`** کپسوله شوند (Repository Pattern).

### ۶.۲. اینترسپتورهای هوشمند (Axios Interceptors)
* **تزریق خودکار توکن احراز هویت:** در اینترسپتور درخواست (Request Interceptor)، توکن دسترسی معتبر (Bearer Token) به صورت خودکار به هدر `Authorization` اضافه شود.
* **مدیریت خطای ۴۰۱ و تمدید بی‌صدا (Silent Refresh Token):**
  * در صورت دریافت خطای ۴۰۱، در صورتی که امکان تمدید توکن (Refresh Token) وجود داشته باشد، درخواست به صف انتظار منتقل شده و پس از دریافت توکن جدید مجدداً اجرا شود.
  * در صورت ناموفق بودن تمدید، اطلاعات نشست پاک‌سازی و کاربر با ذخیره مسیر فعلی (جهت بازگشت بعدی) به صفحه ورود هدایت شود.
* **لغو هوشمند درخواست‌های تکراری:** پیاده‌سازی مکانیزم لغو درخواست‌های هم‌نام قبلی به وسیله `AbortController` در زمان ارسال درخواست جدید.

### ۶.۳. استانداردسازی پاسخ‌ها و DTOها
* کلیه داده‌های دریافتی از سرور باید دارای تایپ مشخص Response DTO باشند.
* در صورتی که ساختار داده سرور با نیازهای فرانت‌اند تفاوت دارد، تبدیل داده‌ها باید در توابع نگاشت (Mappers) انجام گیرد و داده خام وارد استور یا کامپوننت نشود.

## ۷. استانداردهای مدیریت استیت با Pinia

### ۷.۱. استفاده از الگوی Setup Store
* تمام استورها باید بر اساس الگوی Setup Store تعریف شوند:
  ```typescript
  import { defineStore } from 'pinia';
  import { ref, computed } from 'vue';
  import type { User } from 'src/types/user';

  export const useUserStore = defineStore('user', () => {
    const currentUser = ref<User | null>(null);
    const isAuthenticated = computed(() => currentUser.value !== null);

    function setUser(user: User): void {
      currentUser.value = user;
    }

    function clearSession(): void {
      currentUser.value = null;
    }

    return {
      currentUser,
      isAuthenticated,
      setUser,
      clearSession,
    };
  });
  ```

### ۷.۲. اصل ایمن‌سازی و تغییرناپذیری داده‌ها (Immutability)
* وضعیت استورها نباید به صورت خودسرانه و مستقیم از داخل کامپوننت‌ها جهش پیدا کند (`store.items.push(...)` ممنوع است). هرگونه تغییر وضعیت باید منحصراً از طریق Actionهای تعریف‌شده در استور صورت پذیرد.
* برای خروج کاربر یا ابطال نشست، تمام استورها باید دارای اکشن استاندارد بازنشانی (`$reset` یا `resetState()`) باشند.

## ۸. استانداردهای بومی‌سازی زبان فارسی و راست‌چین (Persian & RTL Core)

### ۸.۱. استفاده اجباری از خصوصیات منطقی CSS (CSS Logical Properties)
* در سراسر استایل‌ها و استایل‌های سفارشی، استفاده از جهات فیزیکی مستقیم (`left`, `right`) ممنوع است:
  * به جای `margin-left` و `margin-right` از `margin-inline-start` و `margin-inline-end` استفاده شود.
  * به جای `padding-left` و `padding-right` از `padding-inline-start` و `padding-inline-end` استفاده شود.
  * به جای `left` و `right` مطلق از `inset-inline-start` و `inset-inline-end` استفاده شود.
  * به جای `border-left/right` از `border-inline-start/end` استفاده شود.

### ۸.۲. استاندارد تایپوگرافی متن فارسی
* **فونت پروژه:** فونت استاندارد فارسی (مانند `Vazirmatn`) به صورت محلی در سورس استقرار یابد.
* **ارتفاع سطرها (`line-height`):** در متون فارسی جهت جلوگیری از تداخل اعراب و سرکش‌ها، ارتفاع سطر باید همواره بین **۱.۶ تا ۱.۸** تنظیم شود.
* **ارقام و اعداد:**
  * در متون عمومی، برچسب‌ها و تاریخ‌های تقویم، اعداد باید به فرمت فارسی نمایش داده شوند.
  * در شناسه‌های سیستمی، کدهای ملی، مقادیر عددی فرمول‌ها و داده‌های تکنیکال، از ارقام لاتین با قلم مشخص استفاده شود.

### ۸.۳. مدیریت متون با `vue-i18n` و پرهیز از Hardcode
* هیچ عنوان، برچسب، پیام هشدار، متن دکمه یا توضیحاتی نباید به صورت رشته خام (Hardcoded String) در کدهای HTML یا اسکریپت نوشته شود.
* کلیه رشته‌ها باید از طریق کلیدهای معنادار فایل‌های ترجمه فارسی در مسیر `src/i18n/fa-IR/` و متد `$t('...')` یا `t('...')` فراخوانی شوند.

## ۹. استانداردهای فرم‌ها، تعاملات و تجربه کاربری (Forms & Interactions)

### ۹.۱. رفتار استاندارد فرم‌ها و ورودی‌ها
* **پشتیبانی کامل از قابلیت Paste:** هیچ اینپوت یا فیلدی (شامل گذرواژه، کدهای تایید OTP، شماره‌های شبا و توکن‌ها) نباید رویداد `paste` را مسدود نماید.
* **رفتار کلید Enter:** فشردن کلید `Enter` در اینپوت‌های متنی باید منجر به ارسال (Submit) فرم شود؛ در فیلدهای `q-input type="textarea"` ارسال پیام با ترکیب `Ctrl+Enter` صورت پذیرد.
* **حفاظت در برابر ارسال مکرر (Double Submit Protection):** دکمه‌های ثبت فرم به محض شروع ارسال باید غیرفعال (`disabled`) شده تا از ارسال درخواست‌های تکراری جلوگیری شود.

### ۹.۲. همگام‌سازی وضعیت با آدرس صفحه (URL State Synchronization)
* پارامترهای ناوبری، تب‌های فعال، فیلترهای جستجو، شماره صفحات جداول (`pagination`) و مرتب‌سازی‌ها باید در Query Stringهای URL بازتاب داده شوند.
* کاربر باید بتواند با کپی کردن URL وضعیت فعلی صفحه را با همان فیلترها و اطلاعات برای دیگری به اشتراک بگذارد یا با دکمه Back/Forward مرورگر به حالت قبل بازگردد.

## ۱۱. آزمون‌پذیری و استانداردهای تست (Testability & Quality)

### ۱۱.۱. نشانه‌گذاری برای تست‌های خودکار (`data-testid`)
* تمام کامپوننت‌های تعاملی، فیلدهای فرم، دکمه‌های اکشن، تب‌ها و ردیف‌های جداول ملزم به داشتن اتریبیوت `data-testid` یکتا و بامفهوم هستند:
  ```html
  <q-btn
    data-testid="submit-registration-btn"
    type="submit"
    label="ثبت اطلاعات"
  />
  ```
* تست‌های E2E (با ابزارهایی نظیر Playwright) و تست‌های تعاملی کامپوننت‌ها باید منحصراً بر پایه این مشخصه انجام شود و هرگز نباید به کلاس‌های CSS یا متن دکمه‌ها وابسته باشند.

### ۱۱.۲. استانداردهای تست واحد (Unit & Component Testing)
* توابع منطقی در `composables/` و محاسبات کمکی در `utils/` باید دارای پوشش تست با Vitest باشند.
* کامپوننت‌های حیاتی و استورهای Pinia باید سناریوهای وضعیت اولیه، تغییر وضعیت و پاسخ به خطاهای شبکه را تحت تست ارزیابی کنند.

## ۱۲. عملکرد، بهینه‌سازی و تقسیم کد (Performance & Code Splitting)

### ۱۲.۱. بارگذاری تنبل صفحات (Lazy Loading Routes)
* کلیه مسیرها در `src/router/routes.ts` باید به صورت داینامیک و تنبل لود شوند:
  ```typescript
  {
    path: 'businesses',
    component: () => import('pages/businesses/BusinessListPage.vue'),
    meta: { requiresAuth: true }
  }
  ```

### ۱۲.۲. بهینه‌سازی رندرهای مجدد
* استفاده بهینه از `computed` به جای `watch` در محاسبات وابسته به داده‌ها.
* استفاده از کلید پایدار و یکتای شناسه عددی/رشته‌ای (`:key="item.id"`) در تمامی حلقه‌های `v-for` و پرهیز جدی از استفاده از ایندکس آرایه به عنوان `:key`.
